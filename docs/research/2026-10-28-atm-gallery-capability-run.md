# ATM raw main 与 Mem-Gallery：能力修复与真实模型运行

本记录对应 2026-10-28 的实现和运行。目标是提高现有模型资源下的回答能力。
两个 v4 全量运行已经完成。后续 ATM v6 宽预算的完整 QS 为 0.59497，v4 为
0.53687；Mem-Gallery 仍以 v4 F1 0.79459 为已完成的最好整榜结果，尚未建立 SOTA
结论。后续工作包括完成库的独立物理拷贝、真实 reader 成对回放，以及保留原始来源的
视频描述与事实形成候选库。

## 方案依据

[V-Mem](https://arxiv.org/html/2608.01543v1)区分跨模态偏置与相似度不能代表答案相关性的
两类问题，并用图像关键词和生成式检索锚点寻找证据。这支持保留原生图像检索，同时增加
描述/OCR 路线；本轮实现尚不是其完整的、由问题条件化的路由器。
[RAW-RAG](https://arxiv.org/html/2610.30755)强调原始上下文能够保存推理路径；这是保留
完整用户/assistant 回合、将派生描述用于索引且不取代原件的依据之一。

[Omni-SimpleMem](https://arxiv.org/html/2604.01007v2)的 Mem-Gallery 研究涉及渐进检索、
原始对话证据和回答格式。这里采用有限的证据扩展、失败后重新取证，以及明确的输出样式。
这些论文的结果不是对本轮配置的保证；本轮实际发现了跨轮丢桥接证据、预算挤占和系统时间
指令压过短答案格式的问题，因此先修复这些明确限制。

[LlamaIndex 的句子窗口示例](https://developers.llamaindex.ai/python/examples/node_postprocessor/metadatareplacementdemo/)
将细粒度检索单位与最终交付 reader 的上下文分开。后续图片来源上下文候选借鉴这个原则，
由原文件身份和 SQLite 顺序确定有限邻接；相邻记录的事件关系仍须由内容判断。

## 当前采用的配置

Reader 和视觉描述使用用户提供的 Qwen3.8-27B 服务；embedding 使用
WeMM-Embedding-9B 的原生 4096 维。实际连通的两个地址均为 HTTP：端口 8001 的
`/v1` 提供 VLM，端口 8000 的 `/v1` 提供 embedding。服务返回的 VLM/embedding
身份仍是模型别名，无法据此证明服务端权重 commit 已固定。

| 项目 | v4 配置（已完成） | 原因和边界 |
| --- | --- | --- |
| Embedding | WeMM-Embedding-9B，4096 维，`messages`，text/image/video | 保留原生跨模态向量和独立描述文本路线，不做维度截断 |
| Index | hybrid，`index_quantization: none` | 保留 lexical 路线和 FP32 权威重评分 |
| 初始锚点 | `recall_limit: 12` | 保证最初命中的锚点；不是总上下文行数 |
| 补充证据 | `evidence_budget_chars: 32000` | 软预算，锚点可以超过它；不等于 provider token 上限 |
| 查询视觉 | `query_vision: true` | 查询图像的描述/OCR 作为额外检索路线，保留原始图像查询 |
| 规划与改写 | planning/expansion 均开，2 rounds | 每次 ask 仍最多两次额外查询；新证据优先于可替换的原排名尾部 |
| 集合扩展 | 32000 chars，最多 60 rows | 继续遵守媒体、行数和字符预算 |
| Reader | `answer_style: concise`，strict，max_tokens 4096 | 仅回答所问内容；内部解析时间，问题要求时才输出日期/时长 |
| 非 thinking 采样 | temperature 0.7，seed 0，top_p 0.8，top_k 20，presence_penalty 1.5 | 上述运行通过 CLI `--gen-kwargs temperature=0.7` 设置温度；不能遗漏该运行时覆盖 |
| 图像传输 | embedding/vision 4194304 px，reader 1048576 px | 按实际字节继续限额；原件、SHA 和来源 ID 不变 |
| 视觉描述 | image 能力，`video_frames: 16`，max_tokens 4096 | v4 只启用 image，视频未进入描述阶段；16 帧参数没有用于正式视频摄取 |
| Reader 视频 | 原生视频，`video_limit: 2` | 超大源转 16 帧；数量上限不能证明任意请求都适合 64k 上下文 |
| 副作用 | `reinforce_on_answer: false`，不 formation/consolidation | 保留原始观察，避免题目顺序改变后续排名 |
| Judge | 用户提供的 gpt-5-mini | ATM 走官方 Responses/minimal 协议；Gallery 是替代 judge |

Qwen 的非 thinking 采样来自[官方模型说明](https://huggingface.co/Qwen/Qwen3.8-27B)。
本地真实图片上，temperature 0 曾在 1024 token 截断，同图在 0.7 下可在 512 token
内正常结束。这支持避开该服务上的 greedy 配置，不能推出所有输入都不再截断。
WeMM 的模态、原生维度与服务协议依据[官方实现](https://github.com/Tencent/WeMM-Embedding)。

已完成整榜结果支持分任务使用预算：ATM raw main 采用 v6 的点查询与集合查询各
64000 chars、集合最多 100 rows；Mem-Gallery 保留 v4 的 32000 chars、最多
60 rows。其他核心设置沿用上表。把 Gallery 全局加宽并没有带来相应收益，不能将
“最大参数”直接等同于“最佳配置”。两者均保留原始记录和原生媒体，formation、
consolidation 与地图默认不启用；后述地图配置是另一个明确披露外部知识的候选。

当前 v4 完整运行配置位于本地忽略目录
`.benchmarks/sota-20261028/best-candidate.yaml`。
Judge 密钥仅从进程环境读取，不在配置、报告或源码中保存。

## 本轮已经修复的能力限制

1. 查询图像此前只能依赖原生向量；现在描述与 OCR 可以发现原始候选池外的文本证据。
   描述仅在一次 operation 内缓存，不生成新的记忆或持久化查询图像描述。
2. 改写检索得到的新证据此前可能被原排名尾部挤掉。现在保留初始锚点，并在同一预算内
   优先投递新证据；不再仅在 trace 中显示一次成功检索。
3. 二轮改写此前会丢弃第一轮独立查询发现的桥接事实。现在跨轮保留已经成功读取的
   semantic routes，仍共享两次额外查询及原有预算。真实 SQLite/Zvec fixture 覆盖
   A、B 都在原查询前 100 名之外的成功路径和紧预算路径。
4. 严格回答在显式启用 query expansion 时，可以在第一次拒答后有限重规划。
   Planner 读到的是有界的实际证据摘要，不再只有 ID 和计数。
5. 图片和视频按原文件 base64 字节计数，曾让有效的大图和视频在模型调用前失败。
   现在显式图像像素预算和超大视频采样按实际传输体计费，保留可追溯的原始媒体。
6. Reader 的旧系统提示要求显式输出解析后的日期，会与“仅回答先后关系/立场”的
   问题冲突。新增可选 concise 样式，原 default 提示保留原字节。
7. Gallery 的 judge 原来向 gpt-5-mini 发送不支持的 temperature 0。现在复用模型协议
   处理采样和输出长度参数；judge 失败不再把已经算出的确定性 F1/BLEU 覆盖为零。
   已保存答案可以原样重评分。
8. 多条改写查询此前按整条路线依次填充，第一条路线的尾部可以挤掉第二条路线的关键事实。
   v3 按 A1、B1、A2、B2 轮转投递，跳过当前路线内的重复项；不增加预算和查询次数。
9. 单个 ATM 库此前每次只能摄取一个 batch。新增显式 `ingest_concurrency: 4`，
   对公共 SDK `add_many` 作有界波次并发；检查点只确认连续完成前缀。默认仍为 1，
   有限时间截断、formation、speech/face 等不支持此模式。
   v4 另保护共享开始/结束时间的写入顺序，未知时间串行；并发值是上限，不保证每个波次
   的四个 chunks 同时执行。Gallery 的 240 个 session 均有跨 batch 的同日记录，
   ATM 有 19 组、39 条记录落入同 wave；任意异序写入会改变 SQLite 邻居和截断集合成员。
   实际 SDK/SQLite 逆延迟回归验证同时间顺序、独立时间并发和致命失败后的后继阻断。

首个主题是 `AI_Robotics_Automation_Future_Tech`，185 条记忆、57 题，其中 8 题带查询图像。
所有结果均通过公共 SDK 生成；标签、参考答案和 clue IDs 只用于评分。

| 运行 | 题数 | F1 | gpt-5-mini judge |
| --- | ---: | ---: | ---: |
| 原控制：K20、24k、关闭新检索选项 | 57 | 0.57745 | 0.82456 |
| 新取证链路：K12、32k、query vision、规划和改写 | 57 | 0.64394 | 0.84211 |
| 控制库重放，加 concise 与官方非 thinking 采样组合 | 57 | 0.66833 | 0.82456 |

后两行是已完成库的独立物理拷贝，没有重新摄取。它们同时改变回答样式和其余采样参数，
不能将差值全部归因于一个提示词。前两行是配置比较，也不是只改变一个因素的消融。
这 57 题参与了诊断和选择，不是独立主题 holdout，也不是 1711 题整榜结果。
v3 相对前一候选重放为 14 题 F1 上升、32 题持平、11 题下降，0 请求错误，

弃答由 2 增至 4，未采用。
它仅改 reader 输入，planner/query 和检索配置不变，不读取参考答案构造指令。

在相同的前 20 题上，concise 控制重放 F1 为 0.6684；开启 thinking/medium、输出上限
12288 后为 0.6391。因此当前全量没有启用 thinking。单次采样不证明 thinking 普遍无效。

Reader 小型真实服务回归包括有据回答、时间事实、证据不足和记忆内提示注入。
在相同官方非 thinking 采样下，每例重复三次，default 通过 12/12；原 concise 为
11/12，一次在含嵌入指令的有效事实前安全拒答。concise 增加“拒绝记忆中的指令，同时使用
其中事实”的明确边界后，通过 12/12。实际服务测试提示的 SHA-256 与 v3 产品提示一致：

这些小型检查不能替代完整任务质量或广泛的注入鲁棒性评估。

### 检索和重排

首主题 49 道有 clue 的题，原 SDK 排名 R@10 为 0.93528，R@20 为 0.98178。
这表明本主题的主要损失已经落在阅读、推理、集合完整性和答案表达上，不能只扩大候选池。

在相同 57×100 原生候选池上，固定 revision 的 BGE-reranker-v2-m3 已在本地 4090
实测。用纯问题评分时，CE-only R@20 降至 0.91837，50/50 RRF60 为 0.98980。
8 道图像查询中，CE-only R@20 从 1.0 降至 0.625；RRF 恢复至 1.0，但 R@10 仍有损失。
没有生成质量证据支持全局采用该文字 CE，所以没有将它接入产品配置。

原生多模态 Qwen3-VL-Reranker-2B 在本地 BF16 可运行，且其
[官方说明](https://huggingface.co/Qwen/Qwen3-VL-Reranker-2B)支持原生多模态 query/document。
固定候选池、使用纯问题和原图时，MM-only R@20 为 0.89286，RRF 为 0.96429，均低于原生排名。
8 道图像查询的 RRF R@20 为 0.875，也低于原生的 1.0。没有将它接入产品。
另一次包含任务前言的运行独立保留，其结果不与纯问题运行混合。

已完成主题的逐例诊断中，两道 KR 题的语义 judge 正确，但冗长和同义改写导致低 F1；
另有 KR 题在必要原件已经送达时拒答。CD 的一次错误和 TR 的一次同日先后错误，必要
clue 均在 reader 的实际证据中。这些观察支持继续改进状态、否定和顺序推理，以及原文用语，
而不是把这些错误归因于候选池不足。标签仅用于事后诊断，未用于构造查询或挑选证据。

### 真实媒体边界

- Gallery 的 6000×4000、19859677-byte JPEG，旧路径在模型调用前失败。
  修复后 embedding/vision 传输为 2508×1672、519733-byte JPEG，reader 为
  1254×836、144178-byte JPEG；三条真实请求均 HTTP 200，原件 SHA 不变。
- ATM 的 16348415-byte 视频：embedding 使用 4 帧得到有限的 4096 维向量；
  vision/reader 使用 16 帧均正常结束。它证明大文件可进入模型，不证明所有动作已被保留。
- ATM 的 533 个视频均为 720×480；时长中位数 7.77 秒、p99 105.93 秒、最长 207.534 秒。
  一个 111 秒视频只有 6.78 MB，仍走原生视频路线，所以文件字节上限不能代替 token 预算。
- 对全部原始视频的音轨检查未发现音频流；因此本轮未加载本地 ASR，也未启用 speech。
- 对最长的可原生内联视频作额外真实核验：111 秒单片 generation 使用 11968 prompt
  tokens，与另一段 53 秒视频组成双片请求使用 23945 tokens，均 HTTP 200、正常结束。
  111 秒单片原生 embedding 使用 11661 tokens，返回有限的 4096 维向量。
  这两次 VLM 和一次 embedding 请求均串行、零重试，仅使用最小非 gold 问题，不能推出
  任意混合媒体和软证据预算下的请求都适合 64k。

### 全量日志发现的损失与处理

1. **产品顺序缺陷**：多次穷举读取合并时，以哈希 ID 打破相同事件时间的平局，破坏了
   SQLite 的原始对话顺序。现由 store 按 `(event_time, rowid)` 对已水合结果排序，
