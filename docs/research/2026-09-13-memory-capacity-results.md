# 第二轮记忆实验：容量边界、来源申报与形成连续性

## 本轮结论

第一轮的小图结果成立，但不足以支持广泛提升的结论。本轮测出了明确的容量退化、
来源申报依赖和形成断点，没有提升默认策略，也没有把有退化的候选加入产品。

最值得继续研究的是**按当前记忆义务寻找完整见证**：证明缓存应服务于当前需要的
不相交证据，Context Compiler 应能选择预算内的完整证明，而形成过程应能恢复
解析当前观察所必需的历史见证。这是一组由结果导出的待验证假设，尚非已完成实现。

本轮沿用现有产品代码，源码集合 SHA256 为
`264e179819e09ecd43c701355bd193335bb8aaa5df98153783972b7e052793f7`。
实验设计及运行修订见[第二轮协议](2026-09-13-memory-capacity-protocol.md)。

## 1. 长历史会耗尽证明，而不只是耗尽存储

容量矩阵包含 7 个宽度、6 个深度、3 类结构、4 种命名，共 **504 个纯算法图**。
最大图有 197 个节点，尚未越过 SQLite 的 256 节点读取上限；默认计算预算仍为
每节点 64 条证明、4,096 步。充足资源对照使用 1,024 条证明、200,000 步，仅作诊断。

| 结构 | 默认预算结果 | 充足预算对照 |
| --- | --- | --- |
| 确有两份独立支持，168 图 | 124 图保留两份；36 图剩一份；8 图没有保留证明 | 168 图均有两份 |
| 共享原始 capture，168 图 | 168 图均为一份支持，无错误佐证 | 168 图均为一份 |
| 共享中间摘要，168 图 | 128 图为一份；40 图没有保留证明，无错误佐证 | 168 图均为一份 |

因此，正例合法学习率在这个容量矩阵中是 **124/168（73.8%）**，并非第一轮小图的
100%。负例没有新增错误肯定，但“因为未保留任何证明而隐藏”和“正确识别一份共享
支持”不是同一个能力。4 种命名变体相关，不是独立自然样本。

126 个结构/宽度/深度组合中，**14 个组合只改变内部节点名就会改变支持数**。
例如 `a = OR(r0...r63); target = a OR z` 中，`z` 是独立原始观察。若 `a` 先计算，
它的 64 条替代证明会占满 target 的缓存，`z` 的证明被丢掉；改变节点名导致工作队列
次序变化时，`z` 又可能先保留。这是确定的资源选择问题，不是随机置信度误差。

公开 SDK 再运行了 8 个代表结构、2 个变体、2 个策略，共 **32 个物理库**。正例中
legacy 可见性为 8/8，候选为 7/8；两者在 8 个负例中都没有错误可见。这个局部矩阵
以 singleton/摘要链为主，未重测第一轮联合情景的收益，不能用它取代第一轮结果；
但它足以否定候选在这些条件下始终不退化的主张。

这 16 对 SDK 运行的写入耗时比中位数为 **1.318**；写入阶段中位数为 legacy 1.430 秒、
候选 1.870 秒。大图证据刷新成本需要继续测量，不能把第一轮小图的约 1.1%
开销外推到长历史。这里是未隔离系统背景负载的局部测量，不是生产延迟承诺。

## 2. 两项计算候选：一个否定，一个仅保留为局部优化

**按顶层评估保留多样性、驱逐最弱证明：否定。** 该原型修复了上述缓存占满案例，
但独立审查构造了另一个默认预算反例：一个摘要有 63 条证明，其中只有置信度 0.2
的证明与第二份评估不重叠；其余 62 条置信度 0.9 的证明都与它重叠。加入第三个评估
时，驱逐最弱证明会删除唯一独立见证，支持数从 2 降至 1，分数从 0.92 降至 0.9。
“覆盖更多评估”不能代替“保留当前结论所需的证据”。该候选未进入产品。

**只比较不同顶层评估的证明对：局部有效。** 同一评估内部的两条证明本来就不能
互相佐证。保持所有有效比较的原有顺序，跳过这些无效比较，在一个 200 步对照中把
支持数从 1 恢复到 2，而没有提高上限。独立原型验证中，4,000 次充足预算调用匹配
独立穷举 oracle；16,000 次有限预算调用未发现分数/支持数退化或超出 oracle。

这项优化仍无法找回已被证明缓存丢弃的 `z`，没有解决核心容量问题。它保留为研究
原型，本轮没有据此修改 store recipe 或宣称突破记忆容量。

## 3. 可见的记忆仍可能无法在预算内交付

SDK 容量样本中，两种策略都只有 4/8 正例的目标进入编译结果。对其中一个宽度 64
的图做事后资源消融：保持 256,000 字符预算，将 item 上限从 64 改为 128。

| 策略 | 64 items | 128 items |
| --- | --- | --- |
| legacy | 目标可见，但未交付；报告 `budget_excluded` | 目标交付 |
| 候选 | 目标可见，但未交付；报告 `budget_excluded` | 目标交付 |

代码中的 `_evidence_closures` 遍历当前 `context.evidence_ids` 的完整引证闭包，尚未
选择一组足以支持结论的 AND/OR 证明。这个图虽有很短的完整见证，全部替代来源的
闭包仍会占据预算。扩大预算说明了瓶颈位置，**不是算法改进**，也没有更改产品预算。
后续应对比完整证明选择与现有闭包，而不能通过省略必要证据来提高交付率。

## 4. 显式来源图无法自行判断现实中的复制

另测了 **16 个来源申报单元**，两种策略结果相同：

| 物理输入 | 来源声明 | 结果 |
| --- | --- | --- |
| 完全相同的复制文本 | 正确 capture 或缺失标记 | SDK 合并为一个观察；重复操作被拒绝，长期判断保持隐藏 |
| 完全相同的复制文本 | 两个错误 capture IDs | 变成两条观察，长期判断错误可见 |
| 同一事件的不同复述 | 正确的同一 capture | 两条观察，长期判断保持隐藏 |
| 同一事件的不同复述 | 缺失或错误 capture | 长期判断错误可见 |
| 两个真实独立事件 | 不同 capture | 长期判断正确可见 |

初始执行器未处理“重复操作被拒绝”这一合法结果，在来源阶段中止；504 个纯图和
32 个 SDK 行已经完整保存。后续脚本保留中止记录，完成原条件，并在调用前另行固定
复述扩展条件。没有修改产品去绕过重复检查。

这里的“同一物理事件”由实验设计给定，不传给产品评分器。证明算法在声明证据图上
可能完全正确，却在现实来源上被误导。后续需要 identity-aware capture 和可撤销的
事件同源提案；仅按文本相似度合并又会误伤真正重复发生的经历，需要成对反例检验。

## 5. 真实形成模型：证据策略没有补上感知连续性

使用已配置的 qwen3.8-27b、现有 Formation 提示、temperature=0、固定 seed、
1,500 输出 token 上限；不调用 answerer，不使用 LLM judge。四类两条观察，每类
比较 batch/sequential、legacy/候选、两次重复，形成 **32 个逻辑实验单元**。
媒体仅为合成文本，嵌入仍为常量，不代表真实感知或检索质量验证。

原自动评分存在两个问题：EVENT 的 subject 合法地可为空，正确的人名可能只在正文；
歧义例又把没有产物的运行错误计作通过。原评分完整保留，但**不适合作为记忆能力
指标**。以下是另行标注的事后语义/引证审阅：逐条检查所有最终输出与错误，不悄悄
替换原评分，也不据此报告一个笼统的总体 accuracy。

| 观察类型，每类 8 单元 | 语义与引证审阅 | 形成失败 |
| --- | --- | --- |
| 第二条明确写 Lin Yue 搬家 | 8/8 正确，必要来源完整 | 0 |
| 第二条明确写另一个人 Chen Rui 搬家 | 7/8 正确，未错绑 Lin Yue | 1 |
| 一个人名之后的 `She moved...` | 0/8 形成有完整引证的具名记忆；4 个逐条单元只留下 `She` | 4 个批量单元 |
| 两个人名之后的歧义 `She moved...` | 4 个逐条单元保留未具名事实；不把失败当安全拒绝 | 4 个批量单元 |

合并后 9/32 单元发生结构化输出验证失败。失败批次保留原始观察，没有提交相应的
衍生断言。已经提交的产物没有观察到错误的具名绑定，这不能掩盖缺失的形成能力。
批量路径有时回复不合法 JSON，有时漏掉必需的 observation item；部分未获接受的
回复虽然写出了人物姓名，却只引用搬家句，没有声明用于解析姓名的先前观察。

16 对 A/B 的首次请求，**解码后的 JSON 请求体结构完全一致**，包括模型参数与
提示。日志没有保存原始 wire bytes，因此不声称字节完全一致。一个单元仍出现 A/B
结构验证结果差异，固定 seed 不保证远程服务确定性；不能将该差异认作证据策略的
因果效果。这些例子主要形成 event/relation，且形成输入仍是当前原始观察，恰好揭示
了巩固算法覆盖不到的上游问题。

批量与逐条请求数、可用上下文不同，因此这个对比是形成边界诊断，不是同预算
重放算法的优劣证明。下一轮若加入历史见证，必须与同预算时间窗口和语义检索作对照。

## 执行偏差、成本和复现

首次脚本把 48 次 formation 预算误用于 HTTP 总数，内部验证重试导致 5 个单元受限。
原 32 条记录保留，只补跑全部 5 个被执行器阻断的单元，不重试真正的模型失败，
不择优采用结果。合计 **37 次物理尝试、56 次 formation 调用、58 次正式 HTTP 请求**，
返回用量为 38,579 输入 token、5,015 输出 token。另有一次未计入正式集的连通性
formation probe。补跑发生在更晚时段，报告不把它伪装成完全同步的配对实验。

本轮 Python 为 3.14.2，使用原 lockfile 恢复所有依赖；不拿绝对耗时与第一轮 Python
3.13 的结果相减。原型和 SDK 容量测试只调用本地常量模型；真实模型请求只包含本轮
合成文本。日志不含请求头、凭据或配置副本。

本地原始材料（按仓库规则位于忽略目录）如下：

- `autoresearch/corroboration-capacity-260913/`：504 图、32 SDK 单元、16 来源单元、4 个
  编译预算诊断单元，包含 manifest、中止记录、完成脚本和逐行结果。
- `autoresearch/corroboration-scale-audit-260913/`：否定的多样性原型、不同评估比较原型、
  独立 oracle 与有限预算审查。
- `autoresearch/corroboration-live-260913/`：原 32 行、恢复 5 行、请求/响应、parsed
  proposals、原评分和 `audited-summary.json`。用恢复结果替换的是预先指定的全部
  5 个受预算阻断单元；原始文件没有改写。

## 接受决定

本轮在 Python 3.14.2 下通过全部 2,251 项测试（394.85 秒），lockfile、Ruff 格式、
Ruff 检查及 mypy 检查均通过。固定版本的 Markdown 检查通过，链接检查覆盖 596 个
链接、零错误（含 8 个重定向）。独立对抗审查核对了原始记录、聚合指标、资源消融和
结论范围；报告保留了执行器中止、评分器缺陷及候选反例。

本轮不改变产品代码和默认开关。否定最弱证明驱逐策略；保留跳过无效比较这一局部
优化的研究证据；将下一阶段集中到三项可独立证伪的机制：按义务查找完整见证、
预算内选择可追溯证明、恢复形成所需的历史身份见证。它们必须同时测漏学、错误绑定、
撤销、来源申报错误和真实模型失败，而不是只提高回答率。
