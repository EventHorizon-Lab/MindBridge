# 第四轮：真实形成与 Context 交付的端到端验证

## 结论

**本轮没有证据证明 v3 改善了真实记忆形成或兼容现有契约的 Context 交付。**
真实形成记录没有触发多源证明搜索的优势；把离线证明选择直接接入当前编译闭包，
在诊断案例中增加了表面交付，却产生未交付的公开引证。完整性检查否定了这项收益。

第三轮的合成图结果仍然成立，但“内部能够找到完整证明”不等于“真实形成已经产生
这种图”，也不等于“当前 ContextBundle 能完整表达并交付选定的证明”。本轮验证了
这两个边界，而没有把失败重新定义为成功。设计与修订见[实验协议](2026-09-13-live-context-protocol.md)。

## 1. 真实模型形成：结果一致，上游问题仍在

使用现有 qwen3.8-27b、原 Formation 提示、temperature=0、固定 seed、1,500 输出
token 上限，执行四组各六条合成自然文本。共 **24 次 FORM、24 次 HTTP**，用量为
15,513 输入 token、1,559 输出 token。没有回答模型、LLM judge 或追加重试实验。
服务没有抛出模型异常，但三个原始提案缺少 content 字段，被适配器丢弃。

真实提案录制后，在独立 A/B 库中通过公共 SDK 重放相同 typed proposals。A 是现有
independent-v1，B 是研究进程中的 v3。仅按输入位置重绑来源 ID，不修改模型内容。
排除实际写入时间后，四组 A/B 的完整 SDK 记录逐项一致。

| 固定目标 | A 形成通过 | B 形成通过 |
| --- | --- | --- |
| 明确重复偏好与经历 | 2/2 | 2/2 |
| 不同人物的同类偏好 | 2/2 | 2/2 |
| 单一人物后的跨次代词 | 0/5 | 0/5 |
| 两个人物后的歧义代词 | 4/5 | 4/5 |

“通过”是冻结的姓名、事实词与必要引证检查，不是完整语义质量评价。EVENT 的 subject
可以为空，因此同时检查正文与类型字段。歧义目标要求留下有来源、未错误具名的事实；
远程工作提案被丢弃，算失败，不能把空输出记作正确拒绝。另一个丢弃的远程工作提案
在跨次组，第三个是明确重复组早餐观察的 affect 提案。

SQLite 审计发现 **26 条形成记录全部只有一份独立支持**，没有图读取截断。重复
表达落入不同 kind、predicate/value，或独立 EVENT，没有自动汇聚为多源判断。
这批数据没有提供触发 v3 优势的实际形成图，因此不能据零差异断言它在所有真实
分布上无效；同样不能据第三轮小图改善宣称它已改善真实形成。

24 次 former 输入都只有当前一条观察。跨次例中的先前姓名说明没有进入模型输入；
产物保留 She，或没有产物，缺少实名与命名观察的必要引证。v3 在形成提案之后计算
支持，不改变这些输入，无法独自补出缺失的历史身份信息。

## 2. 在这些真实记录上调用 Memory.compile

使用两个重放策略的持久库，对 14 个冻结事实目标，各用三个预算和三种编译模式。
每个模式有 **84 个调用条件**，三模式共 252 次。84 是目标×存储策略×预算的重复
测量，不是 84 个独立自然事实。

- Full：原始递归引证闭包。
- Trim：按 v3 选择证明后缩减闭包成员，保留权威记录字段，作为待证伪候选。
- Guard：只有缩减后仍满足现有完整递归引证契约才采用，否则回到 Full。

| 真实形成记录上的指标 | Full | Trim | Guard |
| --- | --- | --- | --- |
| 目标形成记录有效交付 | 26/84 | 26/84 | 26/84 |
| 无效 ContextBundle | 0/84 | 0/84 | 0/84 |
| 调用耗时中位数，毫秒 | 4 | 6 | 6 |

实际交付 ID 集合逐条件一致。三个预算为 3 items/1,200 chars、6/2,400、24/8,000；
每个预算有 28 个重复目标条件，分别交付 4、8、14 个。每个预算中实际已经正确形成
的目标条件只有 16 个，其余未形成的目标仍计入端到端分母。

这些库使用常量嵌入，结果只能描述固定检索条件下的实际编译行为，不能当作自然检索
性能。耗时未隔离背景负载，不据几毫秒差异声称产品变快或变慢。

## 3. 表面交付增加为何被否定

首先用五个固定结构控制、同样三个预算与模式进行 45 次公开编译。Full/Trim/Guard
各有 3/15 个目标交付，全部 Context 有效。常量嵌入把原始记录排在目标前，小预算
已经被原始记录填满，掩盖了缩减闭包可能产生的契约错误。这个原始结果完整保留。

随后另行固定事后组件诊断：同五个结构、相同预算，使用通用词项哈希文本嵌入建新库，
让精确文本查询可通过 SDK 检索到目标。嵌入没有目标或案例特判，三种模式共享条件；
它不是自然嵌入模型，也不是新的盲测。

| 诊断指标，每模式 15 条件 | Full | Trim | Guard |
| --- | --- | --- | --- |
| 目标出现在结果中 | 3 | 6 | 3 |
| 目标有效交付 | 3 | 3 | 3 |
| 无效 ContextBundle | 0 | 3 | 0 |

Trim 多出的三个交付分别来自 flat OR、联合 AND 的 OR 替代、深层 OR，均缺少公开
evidence_ids 指向的完整来源。render 保留了未交付的来源 ID，compact 将它们标为
reference_only，document 也保留相同引用。仅统计目标出现会把这三个错误当作提升。

独立审查还用常量嵌入构造了更小的纯 SDK 反例，无排名或 consent 注入：三个独立
OR 来源中两个短、一个长，固定 3 items/1,600 chars。Full 与 Guard 拒绝目标，Trim
交付目标和两个短来源，却在公开引证中继续引用未交付的长来源，验证失败。这个事后
反例说明问题不依赖词项哈希嵌入；另存的来源级 consent 故障注入版本不作为当前
产品政策漏洞或新的独立样本。

一个 flat OR 条件中，实际预算是 6 items/2,400 chars；Trim 报价 1,636 chars，
完整渲染为 1,751 字符，局部 JSON 编码为 8,333 UTF-8 bytes，却缺少三个必须交付
的来源。**预算未超限不等于引证完整。**

这也说明必须区分预算度量：当前 max_chars 约束有价 Context 内容，诊断块另计；
它不是整个 document JSON 或 UTF-8 字节的上限。所有实验分别保存这些实际大小，
没有把它们混为同一个“预算通过”指标。

## 4. 对抗审查与 API 边界

独立验证器不调用证明算法，直接检查实际 ContextBundle：每条公开 evidence_ids 都
有完整 hit、递归无环、render/compact/document 一致、权威 content/context 未改写，
以及 items、媒体和公开 chars 契约。Guard 保留了这些约束，交付收益随之消失。

独立控制另外覆盖形成来源的原子预算、低排名竞争值、valid_at、known_at、consent、
多值关系、来源 memory_type、forgotten 和隐藏判断。三种模式各通过 9 个既有断言、
13 个实际 bundle。带 RetrievalScope 的请求明确回退原路径，没有宣称证明选择已经
支持历史 clause 查询；当前 clause loader 不能仅靠逐节点 hydration 保证历史边正确。

关键阻断不是证书内部缺少某个 AND 来源，而是公开表示尚未区分“持久的全部来源”与
“此次交付选择的证明”。依据[当前编译契约](../context-compilation.md)和
[记忆来源语义](../memory-types-time-and-decay.md)，evidence_ids 是权威来源并集。
不能为了通过评分直接改写它，也不能把预算外附件当作已经交付给 Agent 的证据。

## 5. 接受决定与下一项可证伪假设

本轮否定将 Trim 作为兼容现有 API 的改进。保留 v3 的内部证明搜索研究价值，不推广
产品默认策略；不把 26/84 的零差异说成更强，也不把无效 bundle 的出现率当作收益。

结果导出两项需要分别验证的机制，而非已完成能力：

1. 形成之前恢复必要历史见证，并在同预算下与时间窗口、语义检索对照；检查代词绑定、
   歧义保留、错误归人和撤销。没有形成连续性，多源证明算法往往没有可用的图。
2. 显式的证明携带交付协议，保留权威来源，同时表达选定 clause、完整支持、独立性和
   count/confidence 的共同义务；证书必须计入实际 Agent 输入预算，并保留 scope、
   consent、冲突与逐个中间断言的支持。它需要单独的公共契约设计与端到端实验。

## 复现材料

所有实验位于忽略目录 `autoresearch/corroboration-context-live-260913/`：

- `formation/`：冻结案例/预算、请求、真实提案、失败、A/B 重放、支持图和 12 个持久库。
- `compiler_probe.py`：研究进程的 Full/Trim/Guard 接入，不改产品文件。
- `compile-results/`：297 次主编译（252 真实记录条件、45 结构控制）的完整输出。
- `rank-diagnostic/`：另行固定的 45 次排名诊断，保留全部结果与 manifest。
- `adversary/`：独立实际 bundle 验证器、scope/consent 等控制与反例。

独立审查重新读取并核验了主实验与排名诊断的全部保存输出，统计与上述结论一致。
验证器之后仅增加 Path 的 JSON 序列化支持；主实验版本另存为
`adversary/validate_bundle_primary.py`，哈希与调用前 manifest 一致。唯一差异及两个
版本的哈希记于 `validator-amendment.json`，原结果与 manifest 没有覆盖。

这里使用真实模型处理合成文本，仍非机器人多模态实地采样；常量或词项哈希嵌入均不
代表真实检索质量。固定文字评分有语义覆盖边界，所有原始输出可供人工复核。产品
源码集合 SHA256 仍为 `264e179819e09ecd43c701355bd193335bb8aaa5df98153783972b7e052793f7`。

验证：Python 3.14.2 下全部 2,251 项测试通过（390.06 秒），lockfile、Ruff 格式与
检查、mypy、git diff 检查通过。固定版本 Markdown 检查通过；链接检查覆盖 605 个
链接、零错误（8 个重定向）。研究有效性由独立实验与保存输出审计验证，不以产品
回归测试通过替代机制收益证据。
